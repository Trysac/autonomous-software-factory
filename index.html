The problem

Your backlog of useful tools never gets built.

Every team has a list of small, valuable pieces of software that nobody has time to write properly. AI can write code, but not code you can trust in production without someone checking every line.

Senior time goes to plumbing

Parsers, validators, CLIs and integrations eat weeks that should go to the product.

AI output is unverified

A chat assistant writes plausible code; nobody runs the tests, the audit or the security scan.

Costs are a guess

Model spend is invisible until the invoice arrives, and one provider means one point of failure.

The factory treats models as workers, not oracles: a deterministic pipeline decides what is accepted, under a hard budget, and a human approves the work before it starts and reviews it before it merges.

How it works

Eight steps, two of them human.

The models write and correct code; the factory decides what is accepted. Nothing reaches a repository without passing the same gates a senior team would demand.

Approve

A human selects and approves each specification before anything is built.

Plan and budget

Every item is estimated against a monthly budget with a worst-case reservation.

Generate

Code, tests and documentation are generated in batch, overnight, at the lowest price tier.

Quality gates

Lint, format, types, tests and coverage, docs standard, secret scan and dependency audit.

Correct

A bounded correction loop fixes failing gates with file-level tools only, never a shell.

Independent audit

A separate read-only reviewer checks the result against its specification.

Publish

One clean, squashed commit per pull request; the factory never pushes to main.

Review

A human reviews and merges. CI re-runs the gates on Linux and Windows.

Roles

A team of specialised roles, not one prompt.

Like a human engineering team, the factory splits the work into roles. Some are models with narrow permissions; the rest are deterministic code that no model can talk its way around. Each role is versioned, and each line can bind a different model to it.

Quality

Engineered like production software.

The utilities are small, but they are built to the standard of systems that handle real data and real money.

Security by default

Defences against SSRF, zip bombs and malicious XML entities, strict size limits, errors that never leak secrets, and a written threat model per utility.

Zero runtime dependencies

Most utilities depend only on the standard library, which keeps the supply-chain surface small and the code easy to audit.

Documentation that answers questions

Each README states the problem, installation, a real example, the public API, error codes and when not to use it, backed by architecture decision records.

Guardrails on the factory itself

Path allowlists, protected configuration, secret redaction in every log, history scans before publishing and a hard spending cap that pauses the queue.

Measured, not estimated

Tokens, calls, cost per phase, gate time, fix rounds and lead time are recorded per utility and rolled into analytics after every run.

It learns from every run

Each run produces written lessons; it pauses every few projects for review, and the lessons that repeat become rules or checks before the next run.

Client work

Built for client work, not only open source.

Every project declares how it will be distributed: public open source, private internal, built for a client, or a commercial product. The factory turns that into rules it enforces on its own, before any code leaves the machine.

Client code stays with compliant providers

Confidential projects are only routed to model providers that do not train on inputs and offer zero data retention. The planner refuses any other route.

License gates on every dependency

Each profile has an allow, review and deny list of licenses. Copyleft or non-commercial dependencies never slip into a product meant to be sold.

Tools used, never shipped

Scanners and test tools run inside the factory and are never bundled into deliverables, so their licenses stay with the factory.

Assembly lines

One factory, any model provider.

Each assembly line binds the same pipeline, gates and audit to a different provider, with its own models per role, prices, budget and price window. Each line runs with its own driver and lock: a line that is missing a key or over budget simply stands still; it never stops another line. Four lines have run; three more are built and waiting.

Questions

Frequently asked.

Which models does it use?

Production runs have used Anthropic Claude (line A), Google Gemini (line B), DeepSeek (line C) and Gemini on Google Vertex AI (line D); lines C and D are still running. Lines for OpenRouter and two independent self-hosted lines, one on a rented cloud GPU and one on a local laptop GPU, are built and use the same pipeline and gates.

Does confidential code leave my control?

Each project declares its distribution. Client and internal projects are routed only to providers that do not train on inputs and offer zero data retention; the planner refuses any other route.

What does the human actually do?

Approves every specification before anything is built, and reviews and merges every pull request. The factory never pushes to a main branch.

What do the cost figures include?

They are the measured model API cost per delivered project, including generation, corrections, audit and documentation. They are not a price quote for client work.

How are licenses handled?

Every dependency is checked against the project's license profile, and factory tools are never bundled into deliverables. The open-source utilities on this page are MIT-licensed.
